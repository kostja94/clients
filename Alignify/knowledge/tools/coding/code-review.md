## 词汇锚点

- **Code review / 代码审查**：在合并前由人工或工具对 **diff**、设计意图与风险做检查；目标是缺陷、安全与可维护性在**进入主分支前**被发现。
- **AI code review**：用 **LLM** 与/或 **静态/语义分析** 对 **PR/MR** 或本地变更做自动或半自动审阅；常见输出为行内评论、摘要、修复建议或与 **CI** 联动的检查项。
- **Diff-only vs full-repo context**：仅看补丁与「索引整个仓库 / 构建代码图」在召回复杂逻辑问题、跨文件影响时能力不同；厂商常强调后者为差异化。
- **Stacked PRs / 堆叠合并请求**：将大改动拆成有序、可独立审查的小 **PR** 链，降低单次审查认知负荷；部分平台把 **CLI、队列合并、审查收件箱**与 **AI 评论**绑在同一产品里。
- **Merge queue / 合并队列**：按依赖顺序将已通过检查的 **PR** 入主分支，减少竞态与「绿了又红」；与 **AI 审查**可并列存在于同一工作流。
- **Human-in-the-loop**：行业共识是 **AI** 辅助审查**不**等于免审；高风险变更、架构与安全边界仍依赖人工决策与放行。
- **Code Review Bench**：社区/第三方出现的**基准名称**（不同榜单参数不同）；厂商首页常引用「precision / recall / F1」等表述——**不宜**跨榜单直接比「第几名」而不读方法论。
- **Governance / rules system**：把团队规范、合规条款编码为可执行规则（自然语言或配置），在 **IDE** 与 **PR** 两侧统一执行，常与「企业采购」叙事一起出现。

## 专题对照 / 扩展定义

| 维度 | **传统人工审查** | **AI 辅助审查** |
|------|------------------|-----------------|
| **一致性** | 依赖评审者状态与经验 | 可对每条 **PR** 跑相同检查基线；需注意模型幻觉与漏报 |
| **成本** | 资深工程师时间昂贵 | 前置筛选评论、缩短人类阅读路径；需配置噪声与优先级 |
| **上下文** | 评审者脑中「系统全貌」不一 | 强依赖工具是否拉全仓库/工单/图谱；否则仍是「加强版 lint」 |
| **责任** | 明确到人 | 合并不应默认「AI 已通过」；审计与合规仍要流程 |

| 维度 | **偏「PR 机器人」** | **偏「审查 + 交付工作流」** |
|------|----------------------|------------------------------|
| **典型能力** | 打开 **PR** → 评论与建议 | **Stack**、**merge queue**、收件箱、指标、与 **Agent** 同一界面 |
| **买家心智** | 在现有 **Git 托管**上「加一层 AI」 | 愿意换用或深度嵌套「从分支策略到合并」的一套工具 |

## 问题域（为何会出现这类产品）

- **审查瓶颈**：**PR** 堆积、时区与人力不均导致合并延迟；希望用自动化拉高「首轮反馈」覆盖。
- **AI 写码普及**：生成代码更快，审查侧需要同等速度的**风险扫描**与风格对齐，否则技术债与漏洞面上升。
- **合规与标准落地**：安全编码、许可证、内部 **API** 规范等需**可重复执行**的检查，而非仅靠文档与自觉。
- **跨仓库影响**：微服务与多仓场景下，单 **diff** 不足以判断连锁影响；产品叙事向「图谱 / 知识层」延伸。
- **与编码 Agent 配套**：**Cursor / Claude Code** 等生成路径变短后，团队需要「统一验证层」避免多 **Agent** 各说各话。

## 能力栈（概念拆分，非单一厂商功能表）

- **补丁级分析**：语法、明显逻辑错误、常见漏洞模式、风格与测试缺口提示。
- **仓库级上下文**：依赖图、调用关系、历史 **PR** 评论学习到的团队习惯。
- **规则与策略**：路径过滤、自定义指令、英文/自然语言规则、与组织策略绑定。
- **工作流集成**：**GitHub / GitLab / Bitbucket / Azure DevOps**、**CI**、**IDE**、**MCP**、聊天式追问与修复循环。
- **治理与部署**：**SOC 2**、自托管、无训练/无留存声明、**SSO**、审计日志——企业采购常见检查项。

## 形态谱系（与具体品牌解耦）

- **托管 Git 内嵌应用型**：以 **GitHub App** 等形式_comment on PR_，配置多为 **YAML** 或控制台。
- **审查 + 分支/队列平台型**：在 **stacked PR**、**merge queue**、收件箱层面一体化，**AI** 为其中一层能力。
- **「上下文层 / 架构图谱」型**：强调跨服务、工单与文档的统一上下文，审查与规划、生成共享同一知识模型。
- **验证层 / Agent 编排型**：多 **Agent** 并行审 **PR**、可接 **MCP**、与编码 **Agent** 循环直到评论清零；部分附带**自动生成/运行测试**（如沙箱内测）。
- **本地与左移**：在提交或 **IDE** 内先跑审查，减少 **PR** 往返。

## 风险 · 合规 · 工程治理（外部框架可对照，非法律意见）

- **假阳性与噪声**：过多低价值评论会导致开发者忽略真正问题；需调规则、严重级别与路径过滤。
- **漏报**：**AI** 与静态规则均不能保证安全完备；高危模块仍需专项审计与渗透测试。
- **数据出境与代码处理**：仔细阅读「是否存储」「是否用于训练」「是否支持私有化」；金融与国防客户常强制自托管或单租户。
- **许可与第三方代码**：审查建议可能涉及复制上游片段时的许可证兼容性——工具提示**不能**替代法务流程。
- **基准营销**：「Bench 第一」类表述随**模型版本、数据集与阈值**变化；采购应做**试点仓库**而非只看首页数字。

## 落地碎片（无先后）

- 先定义「哪些 **PR** 必须人工二审」（权限、支付、加密、核心架构）。
- 从单团队、单仓库试点，统计：**评论采纳率**、**CI 失败前拦截率**、**审查耗时**再扩面。
- 把 **AI** 评论与 **CI**（测试、**SAST**、依赖扫描）分层：**谁否决合并**要有明确优先级。
- 定期复盘误报/漏报样例，更新 `.yaml` / 规则与自然语言说明，避免配置僵化。

## 工具与产品类型（检索里常与 AI code review 混排的品类；非穷尽）

| 类型（英文常检索词） | 典型包含什么 | 备注 |
|----------------------|--------------|------|
| **AI PR reviewer** | 打开 **PR** 即触发、行内评论与摘要 | 与 Git 托管深度集成 |
| **Stacked PR / merge queue 套件** | 小步 **PR**、有序合并、审查收件箱 | **AI** 常为增值模块 |
| **SAST / dependency scanning** | 已知漏洞模式与供应链 | 与 **LLM 审查**互补，非替代 |
| **IDE 内联审查** | 保存前提示 | 「左移」减少 **PR** 噪声 |

### 对比与测评（第三方；观点非官方）

横向盘点类文章常从 **集成深度（仅 PR vs 含分支策略）**、**上下文范围（diff vs 图谱）**、**噪声与严重级别可调性**、**私有化与合规**、**计费方式（按席 / 按次 / 开源额度）** 切入。**Graphite** 与纯「PR 机器人」相比更重**工作流**；**Bito**、**Greptile** 常见叙事是「全库/全系统上下文」。**CodeRabbit** 在第三方介绍中常强调**采用面与多平台**；**Baz** 等引用 **Code Review Bench** 时，对比前请阅读**同一基准版本与任务定义**。
