# 知识块模板 · 结构参考

本模板从 30 份 `knowledge/tools/` 文档中归纳而来。各节按出现频率排序；**并非每个文档都必须含所有项目**，但覆盖越全，读者越容易跨品类对照。

**注**：本模板为 Alignify 知识库内部写作工具，**非**面向读者的输出页面。

> **使用前必读**：方法论硬约束见 [`../README.md`](../README.md) 第一章；当前 slug 对应关系与缺口跟踪见 [`README.md`](./README.md)。

---

## 模板大纲

```
H1 # {主题} · 知识块（非线性笔记）

【元数据块】
1. 材料范围（含整理日期）        ← 必需

2. 站内对照（Alignify 正式页链接） ← 强烈推荐；若该 slug 已上线则必须

3. Tools 关键词与 slug 映射       ← 若已在 tools-pages-config 中则必须

4. 【可选】与相邻 slug 分流表     ← 涉及 2+ 个易混品类时推荐

5. 以下条目可任意顺序阅读；不是文章体例

【核心概念块】
6. 词汇锚点（加粗术语定义）       ← 必需

7. 专题对照 / 扩展定义（对比表格）  ← 有易混相邻品类时强烈推荐

8. 问题域（为何会出现这类产品）    ← 必需

9. 能力栈（概念拆分，非厂商功能表） ← 强烈推荐

10. 形态谱系（与具体品牌解耦）     ← 强烈推荐

11. 风险 · 合规 · {治理/伦理/…}   ← 必需

12. 落地碎片（实践建议）          ← 强烈推荐

【工具与索引块】
13. 工具与产品类型（品类表格）     ← 强烈推荐

14. 外链索引（URL 列表 + 对比与测评）← 必需

15. 延伸阅读与参考材料           ← 强烈推荐

【LLM 系列特有块】（仅 LLM 评测类文档）
17. 示例快照（第三方榜单摘录）     ← LLM 系列专用

18. 每公司一条：Top N（去重排行）  ← LLM 系列专用

【行业注记】（极少数文档）
19. 行业注记（厂商重大发布专项）   ← 仅 image-generator.md 有
```

## 各节写作指引

### 1. 材料范围（必需）
格式：
```
**材料范围**：{来源说明}；**未**引用 Alignify 站内文章或站内 JSON 内容稿。网摘整理日期 {YYYY-MM-DD}。
```
示例：
```
**材料范围**：公开网络检索（厂商博客、安全评测、行业对比文与社区讨论摘要）；**未**引用 Alignify 站内文章或站内 JSON 内容稿。网摘整理日期 2026-04-18。
```

### 2. 站内对照（slug 已上线时必需）

> **2026-06 起**：新文以 **`/blog/{slug}`** 为准；历史 Tools 页仍为 **`/tools/{slug}`**。

格式（Blog 新文，2026-06 起）：
```
站内对照：[alignify.co/blog/{slug}](https://alignify.co/blog/{slug}) · `content/blog/en|zh/{slug}.json`
```

格式（历史 Tools 页）：
```
站内对照：[alignify.co/tools/{slug}](https://alignify.co/tools/{slug}) · `content/tools/en|zh/{slug}.json`
```

若 slug 尚未上线，用「待上线正式页时对齐（新文优先 `/blog`）」代替。

### 3. Tools 关键词与 slug 映射（已配置时必需）
格式：
```
**Tools 关键词与 slug 映射**：[alignify-keywords-tools.md](../../keywords/alignify-keywords-tools.md)（锚点 [`#{slug}-tools`](../../keywords/alignify-keywords-tools.md#{slug}-tools)）
```

### 4. 与相邻 slug 分流（可选，推荐在品类易混时使用）
用 markdown 表格列出 `slug` 与 1-2 个相邻 slug 的差异，维度包括：
- 典型买家问题
- 交付形态
- 验收核心

*参考*：search-engine.md 的「与相邻 slug 分流」表、web-scraping.md 的「与专册分工」表。

### 5. 以下条目可任意顺序阅读（保持体例一致）
固定写法：
```
以下条目可任意顺序阅读；**不是**文章体例，无「第一章、第二章」叙事线。
```
个别文档简化为 `无「第一章、第二章」叙事线` 或 `无叙事主线`，建议统一。

### 6. 词汇锚点（必需）
加粗每个术语，用中文给出定义，英文术语保留原词。格式：
```
- **{术语}**：{定义}。{必要时补充与易混概念的区分}。
```
如果品类本身有术语混用问题（如 avatar 既指数字人也指头像），在首条就厘清范围。
*参考*：avatar.md 第一条直接锚定 slug 含义并分流到 headshot-generator。

### 7. 专题对照 / 扩展定义（推荐）
用于展示品类内的关键二分（如「Vibe coding vs AI coding」「T2I vs I2I」），或与相邻品类的分界。用 markdown 表格。

### 8. 问题域（必需）
无序列表，每条解释一个「为何会出现这类产品」的根本原因。建议每条聚焦一个动力（如「标签爆炸」「搜索意图上移」），而非展开流水账。
*参考*：browser.md 的 6 条问题域结构清晰、各条不重叠。

### 9. 能力栈（推荐）
概念拆分解耦，不以单一厂商的功能表为导向。避免写「某产品可以 X」，而是写「这类产品在 X 维度上的常见差异是...」。
*参考*：geo.md 的能力栈覆盖了近 10 个维度的概念拆分，粒度最细。

### 10. 形态谱系（推荐）
与具体品牌解耦的类型划分。每条描述一类产品形态的核心特征，而非罗列竞品名。
*参考*：agent-for-desktop.md 的谱系最系统——给出了 6 种 Type。

### 11. 风险 · 合规 · {后缀}（必需）
固定前缀 `风险 · 合规 · `，后缀根据品类定制：
- 工程治理：agent-skills, code-review, authentication, headless-browser, agent-for-desktop
- 版权与伦理：image-generator, notes-generator
- 未成年人/心理依赖：character-chat
- 数据/隐私：大部分通用

*建议统一格式为*：`风险 · 合规 · 治理（外部框架可对照，非法律意见）`

### 12. 落地碎片（推荐）
实操导向的无序列表，每条是一个可操作的行动建议。

### 13. 工具与产品类型（推荐）
Markdown 表格列出检索词常混在一起的品类，避免读者把不同类型混为一谈。
列：`类型（英文常检索词） | 典型包含什么 | 备注`

### 14. 外链索引（必需）
URL 列表 + 对比与测评。URL 表格式：
```
| 名称 | 一句话 | URL |
```
后接 `### 对比与测评（第三方；观点非官方）` 小节，汇总社区与媒体常见观点。

### 14a. 参考来源质量标准（强烈推荐）

外链索引和延伸阅读中的 URL 应按以下优先级选择，拒绝低权威来源：

**可用来源类型（优先级从高到低）：**

1. **学术论文与预印本**（arXiv、ACM、IEEE、CVPR 等）——经过同行评审或来自公认研究机构。适合引用底层技术（如 DreamFusion、3D Gaussian Splatting）。
2. **权威市场研究报告**（Gartner、IDC、Research and Markets、QYResearch、Meticulous Research 等）——适合引用市场规模、预测数据。
3. **官方文档与 GitHub 仓库**（工具官网文档、开源项目 README、官方技术博客）——适合引用产品功能、API、许可证条款。
4. **知名科技媒体与行业分析**（TechCrunch、The Verge、Ars Technica、Stratechery 等）——适合引用行业动态、收购事件、趋势分析。
5. **厂商官方博客与白皮书**——适合引用产品发布、技术路线图，但需在正文中标注"据厂商公开资料"以区分独立来源。

**明确拒绝的来源：**

- 个人论坛与社区（Indie Hackers、Reddit、Hacker News 评论、知乎、V2EX 等）——无编审流程，不可作为事实依据。
- 中文技术社区（CSDN、掘金、博客园、简书等）——内容质量与事实核查标准不统一。
- 个人博客与 Medium（除非作者是可验证的领域专家且文章有实质引用）——例外情况需在正文中标注作者身份。
- 营销落地页与联盟营销测评——利益冲突，不可作为独立来源。
- 社交媒体帖子（Twitter/X、LinkedIn、微博等）——不可追溯、不可验证。

**注意事项：**

- 同一份知识块中，外链索引与延伸阅读可交叉引用（如学术论文同时列入两处），但避免同一 URL 在不同条目中重复出现。
- 第三方对比与测评小节（§14 "对比与测评"）可引用社区讨论作为行业观点综合，但**不**以论坛帖子作为事实断言。需标注"观点非官方"。
- 中文知识块的中文参考来源优先使用英文权威来源（学术论文、市场报告），而非中文网站翻译或转载版本。
- 所有 URL 在使用前需验证可访问性；失效链接应及时替换或移除。

### 15. 延伸阅读与参考材料（推荐）
按分类列出站外资源，遵循 §14a 的来源质量标准。

## LLM 评测五轴特有结构（2026-06 起）

| 文件 | 职责 |
|------|------|
| [llm.md](./llm.md) | **Hub**：五轴分流、读榜清单、共享治理、行业格局叙事 |

| 四专轴 `llm-for-*` / `multimodal-llm` | 轴内词汇、基准谱系、选型落地；**禁止**复制完整 Top N 表 |

### 专轴应链快照，而非自建 Top N

```markdown
**排行快照**：见 [llm-leaderboard-snapshots.md](./llm-leaderboard-snapshots.md) §{轴名}（快照 YYYY-MM-DD）。
```

### 专轴禁止项

- **不要**在各专轴重复「与相邻 slug 分流」四列表——用 hub §五轴总分流。
- **不要**在各专轴重复 hub 级「风险 · 合规 · 治理」长段——只保留 2–3 条轴特有风险。
- **不要**强制添加「工具与产品类型」表（讨论的是基准而非产品品类）。

## 创建新知识块的操作步骤

> **方法论硬约束**：见 [`../README.md`](../README.md) 第一章——独立来源、不从已有文章取材、增量原则。
> **当前缺口**：见 [`README.md`](./README.md) § 已知结构缺口清单，了解哪些已有文档需要补全。

1. 从本模板大纲复制结构，按品类填充各块
2. 先写**必需**项（材料范围、词汇锚点、问题域、风险合规、外链）
3. 再补**推荐**项（能力栈、谱系、落地碎片、产品类型表）
4. 最后加**可选**项（分流表、对照表）
5. 如是 LLM 评测品类，额外准备基准快照与 Top N 表
6. 如果有重大行业事件（如 OpenAI Images 2.0 发布），考虑是否增加行业注记块
