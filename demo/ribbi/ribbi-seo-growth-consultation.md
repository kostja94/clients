## 〇·A、团队策略定调（与执行优先级）

> 以下为团队**当前共识**，后续与 §1–§3 中「通用最佳实践」并存时，**以本节为执行口径**。

| 主题 | 团队判断 | 执行含义 |
|------|----------|----------|
| **品牌词** | 无大问题 | 维持品牌搜索与首位相关工作 |
| **核心产品词（非品牌）** | **尚未锚定** | 主标题中的 *Self-Evolving Creative AI Agent* 属**品牌叙事/概念**，**非典型 SEO 主词**；需在适当时机把 **可检索的产品品类词**（如 AI creative agent、multimodal content、image/video/audio generation 等，以调研为准）写进 **Title/H1/首屏可见文案** 与后续功能页，与品牌句**分工**（品牌句可保留，但不能替代品类词） |
| **外链** | **导航站可上**；**PR 各类型均可** | 渠道不设限；落地 URL 阶段策略见下行 |
| **外链落地 URL** | 功能页与长尾未就绪 | **链接可全部指向首页** `https://ribbi.ai/`（或统一官方入口），待功能页与长尾体系建立后再做**深度链接** |
| **站内** | **节奏**优先 | **不要**在短时间内**批量**上线大量页面（无论人工还是 AI 生成）；避免薄内容、重复模板与索引膨胀，**稳态放量** |
| **站外 UGC** | 对官网 SEO **无所谓** | 团队判断：**站外 UGC 内容**一般不会**损害**网站本身 SEO；若**无效果**也**不视为对站点造成伤害**。（注：各**社交平台**仍有账号与 ToS 风险，与「搜索引擎是否惩罚主站」属不同维度。） |

| **结构化数据** | JSON-LD 使用 `@graph` 多类型并存；存在 **@id 冲突与类型堆叠**问题（见 §6.4） |

| **H 标签** | 存在**层级与可见性混乱**（sr-only H1 + 可见中文 H2/卡片；多语言混排），需统一规则（见 §6.2） |
| **风险备注** | 大量核心文案放在 **sr-only** 时，需避免「仅给爬虫看、与用户可见内容严重不一致」被判定为操纵；建议用户可见区逐步**显性化**关键价值句或与可见 UI 对齐 |

## 1. 官网关键词与结构——还可能遗漏什么？

以下按**优先级**列出常见遗漏项，团队可按已有进度勾选。

### 1.1 关键词层

| 项 | 说明 | 建议动作 |
|----|------|----------|
| **品牌词簇** | Ribbi / Ribbi AI / site: 品牌 + review / alternative / pricing | 维护知识面板实体一致性；Review/比价页若未开放则预留 URL 规划 |
| **品牌概念 vs SEO 主词** | *Self-Evolving Creative AI Agent* 属**差异化叙事**，**不等于**已占位「用户会搜的」核心品类词 | 单独做 **词表**：品牌句保留 + **1–3 个主品类词**（英/目标市场）写入首页与 meta 的**可组合**位置；详见 **附录 A** |
| **品类词** | creative AI agent、AI creative partner、multimodal AI creator、AI image/video/audio generator 等 | 在 **§〇·A** 前提下，**未建功能页前**可先强化**首页与 JSON-LD** 的品类表述；**勿**与短期批量上页冲突 |
| **功能词** | carousel、dubbing、comic、background removal、article to podcast 等 | 与 [ribbi-features.md](./ribbi-features.md) 技能一一对应；每个高价值 skill 理想状态为**独立可索引 URL + 唯一 Title/H1** |
| **竞品/替代词** | X alternative、vs X | 中长期内容/对比页；注意表述合规 |
| **多语言关键词** | 中文 UI 与英文 meta 并存时的 **hreflang / x-default** | 若同一 URL 仅语言切换，需明确 canonical 与重复内容策略 |
| **长尾** | how to、best tool for… | 适合 Blog/Help，反哺内链至 Skill 页 |

**结论**：在未开放全部落地页前，**最大缺口**通常是「**非品牌意图词 → 专用落地页**」的映射；**当前阶段**团队允许**外链与 PR 全部指向首页**；首页需逐步承担 **品牌 + 核心品类词**（见 §〇·A），**Skill/场景页**待体系就绪后再承接长尾与深度链接（**且须遵守 §〇·A 的站内放量节奏**）。

### 1.2 站点结构与内链

| 项 | 说明 |
|----|------|
| **IA 清晰度** | Top Picks / Your Skills / 分类（社媒·视频·视觉…）与最终 URL 规则是否在内部文档与 sitemap 一致 |
| **孤儿页** | 未上线页面勿提交 sitemap；上线后每个重要 URL 至少 **2+ 条内链**（首页、分类 hub、相关 skill） |
| **重复与分页** | 若未来有标签/搜索参数，提前约定 canonical 与 noindex 规则 |
| **Programmatic 页** | 技能数量大时，**列表 hub + 详情** 模板统一 Title/Meta/Schema，避免薄内容 |
| **放量节奏** | 与 §〇·A 一致 | **禁止** short-term 批量上大量页面（人工或 AI）；优先**质量**与**可维护索引**，再扩量 |

### 1.3 页面体验与 E-E-A-T（与 SEO 叠加）

| 项 | 说明 |
|----|------|
| **可见内容与 sr-only** | 逐步让用户可见区出现与 meta 一致的**核心价值命题**，降低「隐藏文案」依赖 |
| **作者/产品主体** | Organization/SoftwareApplication 已部分覆盖；Blog 若上线，**署名、更新日期、About** 强化信任 |
| **帮助文档** | 降低「仅营销页」比例，利于长尾与 Support 搜索 |

## 2. 外链与权重积累——ROI 优先级（经验向排序）

> **团队当前策略**：**导航站**、**各类 PR** 均可；在功能页与长尾未就绪时，**外链一律指向首页**即可（见 §〇·A）。下列为**通用**参考顺序，与团队策略**不冲突**时可作细化。

> 原则：**品牌已起势**时，短期 ROI 往往来自「**强化品牌与转化路径** + **可规模化内容资产**」；纯「为链接而链接」的低质目录长期风险高。下列为**一般**优先级，需结合 Ribbi 目标市场（美区/全球/中文）微调。

### 2.1 第一梯队（通常 ROI / 风险比较均衡）

| 手段 | 渠道/形式 | 为何靠前 | 备注 |
|------|-----------|----------|------|
| **产品内可分享资产** | 用户生成内容带品牌水印、embed、公开案例页 | 自然外链、社交二次传播 | 需用户协议与隐私授权 |
| **官方社媒与社群** | X/LinkedIn/YouTube 官方账号、Discord/Slack 用户群 | 品牌搜索、直接访问、互动信号 | 与 KOL 内容互链 |
| **高质量目录与评测站** | 垂直 AI 工具目录（TAAFT、Product Hunt、G2 类若适用） | 品牌曝光 + 引用域 | 避免垃圾目录农场 |
| **创始人/产品叙事 PR** | 科技媒体、Newsletter、播客 | 权威引用、品牌实体 | 一篇深度稿可多年复用 |
| **文档与开发者/创作者教育** | API/集成、教程、模板 | 自然长尾 + .edu/.org 偶尔引用 | 与产品路线图一致时再扩展 |

### 2.2 第二梯队（有效但需控量与质量）

| 手段 | 说明 |
|------|------|
| **客座文章 Guest post** | 行业博客、创作者经济、营销类媒体；**长尾词**锚文本多样化，避免全精确匹配 |
| **合作伙伴互链** | 模型/API/云厂商、设计资源站；**相关性**优先于数量 |
| **社区真实参与** | Reddit、Hacker News、垂直论坛（遵守各版规则，忌 spam） | 带来流量与偶尔nofollow外链，利于品牌与洞察 |
| **资源页链接 Resource page outreach** | 「best AI tools for creators」类页面 | 需一页一议，拒绝付费垃圾链 |

### 2.3 第三梯队（长尾与规模化，中长期）

| 手段 | 说明 |
|------|------|
| **程序化 SEO 博客** | 每个 Skill 一篇「如何用 Ribbi 做 X」+ FAQ Schema | 承接 long-tail，需防薄页 |
| **多语言内容** | 与产品本地化同步，避免机器翻译堆砌 |
| **案例研究 Case study** | KOL/品牌客户授权案例 | 强 E-E-A-T，可再用于销售与 PR |

### 2.4 刻意靠后的（常见低 ROI 或高风险）

| 类型 | 原因 |
|------|------|
| **批量购买链接、PBN** | Google 反垃圾；品牌站不值得 |
| **无关行业目录群发** | 引用域质量差，可能有害 |
| **纯自动化评论/论坛外链** | 封号与品牌损伤 |

### 2.5 「长尾词」在外链策略里的位置

- **当前阶段（团队）**：功能页未构建、长尾未做 → **外链统一指向首页**合理；锚文本优先**自然句 + 品牌名**，必要时带**品类词**（与 §1.1 主词表一致）。  
- **后续**：长尾由 **Blog/Help/Skill 页** 承接，外链再拆到**深度 URL**；避免过度优化单一 money keyword。

## 3. 可自动化与需特别关注的环节（含「模拟 UGC」盲区）

### 3.1 适合流程化 / 半自动化的「白帽」环节

| 环节 | 自动化程度 | 说明 |
|------|------------|------|
| **索引与收录监控** | 高 | sitemap、GSC、IndexNow（若适用）、上线检查清单 |
| **技术巡检** | 高 | Core Web Vitals、404/重定向、canonical、hreflang |
| **结构化数据校验** | 高 | 富媒体结果测试、批量 JSON-LD 校验 |
| **内部链接建议** | 中 | 基于模板规则：同分类 skill 互链、hub→detail |
| **内容草稿生成** | 中 | AI 辅助首稿，**人工事实核对与合规审** |
| **社媒发布排期** | 中 | 官方账号定时发帖；**KOL 合作条款与素材需人工** |
| **舆情与品牌词监控** | 中 | Alerts for「Ribbi」+ 常见误拼 |

### 3.2 站外 UGC 与 SEO（团队判断）

| 维度 | 团队判断 |
|------|----------|
| **对官网 SEO** | **站外 UGC**（一般意义上的第三方发帖、讨论内容）**通常不直接决定**主站排名；**无效果时**，团队认为**不损害** `ribbi.ai` 本身。 |
| **与站内策略关系** | 与 §〇·A「站内勿批量上页」**独立**；站外 UGC ≠ 站内内容工厂。 |

**补充（非 SEO 维度）**：社交平台仍有 **账号封禁、社区规则、赞助披露** 等风险，与「Google 是否惩罚主站」是两套问题；PR/导航站策略见 §2 与 §〇·A。

**原「模拟 UGC」讨论**：若团队**不**以站外 UGC 作为 SEO 主手段，则资源可继续投向 **PR、导航站、品牌词**；无需在「是否损害 SEO」上过度内耗，**以可衡量渠道 ROI 为准**。

### 3.3 与 KOL 合作叠加 SEO 的注意点

- 争取**描述区与固定评论**中含品牌名与**唯一卖点短句**（非堆砌关键词）。  
- 若视频/帖子**可嵌入官网**或**案例页**，增加**可抓取文本**与**内链入口**。  
- 追踪：**品牌搜索量、首页自然流量、引荐流量（referral）** 是否随活动上升，用于复盘渠道 ROI。

## 4. 建议的下一步（可转为内部 checklist）

1. **核心产品词**：在首页与 meta 中**锚定** 1–3 个可检索品类词（与 *Self-Evolving…* 品牌句分工），见 §〇·A、**附录 A**。  
2. **结构**：列出「将开放」的落地页清单，并为每个 URL 预设 **Title/H1/内链父节点**；**优先补全** `/pricing`、`/features`（或等价聚合页）、`/about`、**公司/法律**入口，避免导航仅指向 `/chat`。  
3. **关键词表**：从 [ribbi-keywords.md](./ribbi-keywords.md) §1–§2 扩展为「**词 → URL → 状态**」；策略叙述以 **附录 A** 为准；**未建页前**首页可先行承接。  
4. **外链**：**导航站 + 全类型 PR**；**链接统一指向首页**直至功能页就绪（§〇·A）。  
5. **站内放量**：**禁止**短期批量大量页面（人工/AI 均适用）；与 §1.2「放量节奏」一致。  
6. **自动化**：上线 **GSC + 爬取监控 + 结构化数据 CI**；内容用 AI 辅助时**控制发布节奏**与质量。  
7. **sr-only 策略**：产品与设计排期，将核心文案**逐步露出**给用户，与爬虫一致。  
8. **hreflang**：按 §6.3 修正（单语站 vs 多语站二选一，禁止三标签同 URL）。  
9. **Schema**：按 §6.4 解除 `@id` 冲突、合并重复产品类型、校验 `SearchAction` 与 `featureList`。  
10. **Heading**：按 §6.2 统一每页 **1 个可见或可访问的主标题**逻辑与层级。

## 6. 补充诊断：核心页缺失、导航、hreflang、H 标签、Schema

### 6.1 核心页面与「完整网站」观感

| 观察 | 影响 | 建议 |
|------|------|------|
| **缺失** 大部分常规核心页：如 **Pricing**、**Features**（或功能总览）、**About**（团队/公司/使命）等 | 商业类查询（*ribbi pricing*、*what is ribbi*）难以有**专用着陆页**；E-E-A-T 中「谁在做这个产品」偏弱 | 至少上线 **Pricing**（或明确「计划与计费说明」页）、**About**（Somasole Inc. 与 Ribbi 关系）、**Features hub**（链到各 Skill/场景）；与 [ribbi-features.md](./ribbi-features.md) 技能树对齐 |
| **导航** 直接进 **`/chat`**，登录后进入产品 | 新访客从搜索/外链进来时，更像**工具入口站**，不利于「先理解价值再注册」的经典转化路径 | 营销首页保持 **独立故事线**；CTA 再进 `/chat`；sitemap 区分**营销 URL** 与 **App URL** |
| **法务与联系** | 若仅 sr-only 页脚，用户与审核方（广告、应用商店）体验差 | Privacy / Terms / Contact **对用户可见**且可索引（或清晰链出） |

### 6.2 H 标签（Heading）混乱——问题与原则

| 问题 | 说明 |
|------|------|
| **sr-only H1** 与 **可见中文 H2** 并存 | 爬虫可见 H1，用户主视觉以中文分类 H2 为主，**语言与层级感知不一致**；读屏用户与可视用户可能得到不同「主标题」体验 |
| **同一页面多强标题竞争** | Title/meta 英文强调 *Self-Evolving Creative AI Agent*，界面以中文分类为主，**主题句分裂** |
| **Skill 卡片标题** 层级需统一 | 卡片应用 **H3** 还是 **带 heading 的 list**，应在组件层固定，避免满屏 `h2` 或跳级 |

**建议（简版）**：

1. 每页 **1 个逻辑主标题**：营销首页可为**可见** H1（或中英文策略统一后的一种语言），减少仅 sr-only 的 H1。  
2. 区块：**H2** = 大分类（社媒/视频/…）；**H3** = Skill 名或卡片标题；避免跳级。  
3. 中英文：要么 **URL 级分语言** + 正确 hreflang，要么 **单页内**明确主语言，避免 H1 英、模块标题全中且无 `lang` 属性（可在根或区块加 `lang`）。

### 6.3 hreflang 配置错误（en / zh / x-default → 同一 URL）

**现状（团队提供）**：

| 标注 | URL | HTTP |
|------|-----|------|
| `en` | `https://ribbi.ai` | 200 |
| `zh` | `https://ribbi.ai` | 200 |
| `x-default` | `https://ribbi.ai` | 200 |

**为何有问题**：

- Google 对 hreflang 的期望是：**同一页面不同语言版本用不同 URL（或明确单语言无需多组标注）**。  
- **三个标签指向完全相同 URL** 时，无法表达「英文版 vs 中文版」，搜索引擎只能视为**重复/自相矛盾**，可能忽略 hreflang 或削弱信任。  
- **x-default** 通常用于「未匹配语言时的默认页」；若与 en、zh 同 URL，三标签**无区分度**。

**修法（二选一，需产品定调）**：

| 策略 | 做法 |
|------|------|
| **A. 实质单语站**（仅一种主语言页面可索引） | **移除** 多余的 `zh`/`en` 互链；只保留 **一个 canonical**；若仅服务英文，**不要**发 `zh` alternate；若 UI 有中英文切换但 DOM 同页，考虑 **不声明** hreflang，改用语种切换 + `lang` 属性。 |
| **B. 真正双语/多语** | **独立 URL**：如 `ribbi.ai/en`、`ribbi.ai/zh` 或子域；每页 **自引用** + 双向 `alternate` + `x-default` 指向默认语区；内容勿全站 duplicate。 |

**结论**：当前配置 **不正常**；在采用 B 之前，建议 **删掉误导性的 en/zh/x-default 三重复**，避免与 GSC 国际定位报告冲突。

### 6.4 JSON-LD Schema（@graph）是否正常——诊断结论

以下为对团队提供的 **`@context` + `@graph`** 结构的审查结论（类型名以 [Schema.org](https://schema.org) 为准）。

#### 合理之处

| 项 | 说明 |
|----|------|
| **Organization** | `Somasole Inc.`、`url`、`logo`、`contactPoint`（`contact@somasole.ai`）有利于**主体与品牌实体**一致 |
| **WebSite** + **publisher** 指向 Organization | 常见组合 |
| **产品侧** 使用 **WebApplication** 或 **SoftwareApplication** 描述 Ribbi、含 `offers`（price 0）在「免费入门」类产品中**常见**（需与真实计费一致，避免虚假宣传） |
| **`applicationCategory` / `operatingSystem: Web`** | 与 Web 产品一致 |

#### 异常与风险（建议修复）

| 问题 | 说明 |
|------|------|
| **`@id` 冲突** | 若 **Organization** 使用 `@id: https://ribbi.ai/#organization`，而 **SoftwareApplication**（或另一类型）也使用 **相同 `@id`**，则违反 JSON-LD 惯例：**一个 `@id` 只能对应一个节点**。团队提供的片段中，存在 **SoftwareApplication 节点带 `@id` …`#organization`** 的写法——与 Organization **共用同一 @id**，属**严重错误**，会导致解析器合并/覆盖语义混乱。 |
| **WebApplication 与 SoftwareApplication 双开** | 同一产品同时用 **WebApplication** 与 **SoftwareApplication**（再加 WebSite）易**重复**；建议 **只保留一个** 作为主 `SoftwareApplication` 或 `WebApplication`，属性合并。 |
| **`WebSite` 上的 `SoftwareApplication` 块** | 若 `WebSite` 内嵌的 `SoftwareApplication` 再次混用 `@id` 或与 `WebApplication` 描述重复，应**收敛为单一 graph 节点**引用 `@id`（`"@id": "https://ribbi.ai/#webapp"`） |
| **`potentialAction` → `SearchAction`** | `urlTemplate: https://ribbi.ai/search?q={search_term_string}` 仅在**站内搜索真实存在且可索引/可用**时合理；若实际无 `/search` 或仅为 App 内搜索，**应删除**或改为真实入口，避免结构化数据**与可见功能不符**。 |
| **`featureList`** | 应为**字符串数组**或规范列表；若实现为带数字前缀的拼接（`0 Self-Evolving…`），可能被解析为**单字符串**而非多条 feature；建议改为 JSON 数组：`["Self-Evolving AI Agent", "AI Image Generation", …]`。 |
| **描述文案不一致** | WebApplication / SoftwareApplication / 页面 meta 之间 **description** 应用**同一套主陈述**或明确主从关系，避免「companion」与「autonomous agent」两套叙事打架。 |

**总评**：**整体意图正确**（公司 + 网站 + 产品），但 **`@id` 唯一性**与**产品类型重复**、**SearchAction 真实性**、**featureList 格式**需修正后，才可称为「健康」的 JSON-LD；否则富结果测试可能报错或无法获得预期展示。
