# 客户文档规范

本规范定义 `demo/` 与 `clients/` 下客户文档的**标准结构**、**质量标准**、**生命周期管理**与 **Agent 自动化流程**。所有客户文件（含 Demo 与正式客户）均遵循本规范；**仅在此处维护，不再另设 clients 版模板**。

文档生命周期：
1. **Demo**（`demo/{name}/`）— 内部知识库 + 向潜在客户展示分析能力
2. **Clients**（`clients/{name}/`）— L3 毕业后迁入，承载真实业务数据与交付方案；允许在七核心文件之上大量定制扩展

### 规范引用路径

相对路径按所在目录选择（`client-template.md` 位于 `demo/` 根目录）：

| 所在目录 | 引用路径 |
|----------|----------|
| `demo/{name}/` | `../client-template.md` |
| `clients/{name}/` | `../../demo/client-template.md` |
| `clients/others/{name}/` | `../../../demo/client-template.md` |
| `clients/others/{name}/{sub}/` | `../../../../demo/client-template.md` |

## §1 文件结构

### 1.1 文件结构选型

| 模式 | 适用场景 | 典型文件数 | 判断标准 |
|------|----------|-----------|---------|
| **单文件** | 初步调研、信息量少（<5 页官网）、仅内部参考 | 1 | 官网 <5 页面、无明确竞品信息 |
| **多文件** | 完整项目、有展示需求、信息量充足 | 7–15 | 官网 ≥5 页面、有可分析竞品 |

**决策规则**：新建 Demo 项目时，先走单文件模式收集基础信息；当主文档超过 **500 行**或出现 3 个以上独立维度时，拆分为多文件模式。

### 1.2 多文件标准结构

```
{name}/
├── {name}.md                           # 主文档：概览、产品、ICP（必选）
├── {name}-keywords.md                  # 关键词策略（必选）
├── {name}-features.md                  # 功能/产品分析（必选）
├── {name}-competitors.md               # 竞品分析（必选）
├── {name}-site-structure.md            # 站点结构（必选）
├── {name}-use-cases.md                 # 使用场景（必选）
├── {name}-growth-strategy.md           # 增长策略（必选）
├── {name}-brand-visual.md              # 品牌视觉（按需）
├── {name}-others.md                    # 杂项（按需，见 §2.8）
├── {name}-{topic}.md                   # 其他高级主题（按需）
├── blog/                               # SEO 博文（按需）
│   ├── {NN}-{slug}-{year}.md
│   └── README.md
└── README.md                           # 文件夹索引（推荐）
```

### 1.3 命名规范

**文件命名**：`{name}-{topic}.md`
- `{name}`：品牌标识，全小写连字符（如 `final-round`、`kusa-pics`）
- `{topic}`：主题英文，全小写连字符
- 中文文档加 `-zh` 后缀

**博文命名**：`blog/{NN}-{英文-slug}-{年份}.md`
- `{NN}`：两位数序号（01, 02…）

## 1. 产品定位

> 很多产品的差异化仅存在于定位上，功能层面差异不大。本表格记录定位维度的结构化信息。

| 维度 | 内容 |
|------|------|
| 品类 | 该产品属于什么品类（一句话） |
| 价值主张 | 为核心用户解决的 Top 1 问题 |
| 竞争替代 | 用户当前用什么方案/工具，为什么转向本品 |
| 差异化锚点 | 与竞品最核心的 1–3 个差异（取自 features.md 中 ★ 标记的功能） |
| 市场位置 | 高端 / 性价比 / 垂直专家？（结合定价和功能广度判断） |

### 1.1 定位简述

2–3 段叙述，覆盖：
- 品类格局 + 本品占据的位置
- 核心用户画像（引自 客户概览 > 目标用户）
- 为什么存在（品牌存在的理由 / raison d'être）

## 2. 产品信息

产品线、受众范围、定价模式摘要（完整功能见 features.md）。

## 3. 关键词摘要

核心关键词 + 品牌词。完整见 [{name}-keywords.md](./{name}-keywords.md)

## 4. 竞品摘要

主要竞品 + 核心差异。完整见 [{name}-competitors.md](./{name}-competitors.md)

## 5. 站点结构摘要

技术栈 + 核心路径。完整见 [{name}-site-structure.md](./{name}-site-structure.md)

## 6. 使用场景摘要

主要 Persona + 场景。完整见 [{name}-use-cases.md](./{name}-use-cases.md)

## 7. 增长策略摘要

核心渠道 + 方向。完整见 [{name}-growth-strategy.md](./{name}-growth-strategy.md)

## 8. 优化建议

SEO/GEO/内容层面的关键建议（1–3 条，具体可执行）。

---

*关联：[keywords](./{name}-keywords.md) | [features](./{name}-features.md) | [competitors](./{name}-competitors.md) | [site-structure](./{name}-site-structure.md) | [use-cases](./{name}-use-cases.md) | [growth-strategy](./{name}-growth-strategy.md)*

*Last updated: YYYY-MM-DD*
```

**写作要点**：
- 客户概览表**必须填满**，不留空
- **定位表 5 个维度从上游文档推导**：
  - 品类 → 从行业 + 功能名推断，搜索验证
  - 价值主张 → 搜索用户评价中的真实表述（禁止凭空编造）
  - 竞争替代 → 搜索"\[品类\] alternatives to \[传统方案\]"
  - 差异化锚点 → 直接从 features.md 中 ★ 标记的功能提取
  - 市场位置 → 从 pricing 信息推断，标注推断依据
- 定位简述保持 2–3 段，不展开成独立文章
- 各节摘要在 3–5 行内完成，用链接引导到子文档
- 优化建议必须具体（"建议创建'X vs Y'对比页"而非"建议优化 SEO"）

**常见错误**：
- ❌ 主文档写得像独立文档，不引用子文档
- ❌ 客户概览表留空
- ❌ 优化建议太笼统

### 2.2 关键词文档 `{name}-keywords.md`

**职责**：关键词策略中心。记录搜索意图分类、搜索量/难度、内容覆盖计划、与功能和场景的承接关系。

**章节模板**：
```markdown
# {品牌名} — 关键词策略

## 1. 核心关键词

| 关键词 | 月搜索量 | 难度 | 意图 | 目标页 | 优先级 |
|--------|---------|------|------|--------|--------|

## 2. 品牌词

品牌名及相关变体。

## 3. 话题簇 / 长尾词

按主题分组，每组建议 5–10 条。

## 4. 意图分类与承接映射

| 意图类型 | 关键词示例 | 建议承接页 | 状态 |
|----------|-----------|------------|------|
| 导航型 | | 首页 / 功能页 | 已承接 / 待建 |
| 信息型 | | 博客 / 对比页 | 已承接 / 待建 |
| 商业型 | | 定价页 / 评测 | 已承接 / 待建 |
| 交易型 | | 注册 / 试用 | 已承接 / 待建 |

## 5. 内容缺口

当前站内未覆盖但有机会的关键词。

---

*关联：[主文档](./{name}.md) | [features](./{name}-features.md) | [site-structure](./{name}-site-structure.md) | [use-cases](./{name}-use-cases.md) | [competitors](./{name}-competitors.md) | [growth-strategy](./{name}-growth-strategy.md)*

*Last updated: YYYY-MM-DD*
```

**写作要点**：
- 每条关键词标注来源工具+日期（如 "Semrush 2026-05"）
- 意图分类至少覆盖 4 类，每类 ≥5 条
- 优先级用 P0/P1/P2 三级，P0 为必须覆盖

**最低深度**：
| 维度 | 要求 |
|------|------|
| 意图分类 | ≥4 类 |
| 每类词条 | ≥5 条 |
| 目标页映射 | ≥80% 词条有映射 |
| 优先级标注 | 全部 |

### 2.4 竞品文档 `{name}-competitors.md`

**职责**：竞品矩阵。直接竞品详细拆解 + 场景级对比 + 差异化机会。

**章节模板**：
```markdown
# {品牌名} — 竞品分析

## 1. 竞品总览

| 竞品 | 定位 | 目标用户 | 核心功能 | 价格区间 | 与本品差异 |
|------|------|---------|---------|---------|-----------|

## 2. 直接竞品详细拆解

每个竞品独立小节：
- 产品定位与核心能力
- 优势与劣势
- 市场份额/流量估算（标注来源+日期）
- SEO/GEO 表现

## 3. 场景级对比表

| 场景 | 本品 | 竞品A | 竞品B | 本品优势 |
|------|------|-------|-------|---------|

## 4. 差异与机会

SWOT 或类似分析。

---

*关联：[主文档](./{name}.md) | [features](./{name}-features.md) | [keywords](./{name}-keywords.md) | [use-cases](./{name}-use-cases.md) | [site-structure](./{name}-site-structure.md) | [growth-strategy](./{name}-growth-strategy.md)*

*Last updated: YYYY-MM-DD*
```

**写作要点**：
- **至少 3 个直接竞品**详细拆解
- **竞品入选标准**：只收录「主要对标竞品」（与本品争夺同一批目标用户/购买场景）且「知名」的产品——满足任一即可：公开融资可查（≥百万美元量级）、或月访问量达十万级（Semrush/SimilarWeb）、或行业公认品类头部；排除泛品类参照物（如 LLM 网关/模型 API 这类不直接对标的网站）与流量/融资均无公开数据的小众初创。每个收录竞品在拆解中标注「入选依据」（知名度的量化证据）
- 流量/排名数据标注来源（Semrush / Similarweb + 日期）
- 场景级对比表至少 2 张（不同使用场景）
- 不确定信息标 `待验证`

### 2.6 使用场景文档 `{name}-use-cases.md`

**职责**：记录官网/产品实际呈现的使用场景事实，并基于事实做分析（Persona 归纳、场景 ↔ 能力 ↔ 关键词映射）。**只写来源明确的内容**，不堆模板化的无关章节。

**章节模板**：
```markdown
# {品牌名} — 使用场景

## 1. 官网场景事实（来源：官网 xx 区块 / 页面实况）

以官网实际文案/角色/卡片为事实来源，逐条记录。若官网有固定句式（如「Today helped a [角色] + [动作]」），保留原句式。

| # | 角色/场景 | 官网文案（原文） | 对应能力 | 资产/URL |
|---|----------|-----------------|---------|---------|

若官网有结构/交互细节（卡片样式、滚动方式等），一并记录在事实小节。

## 2. Persona / 方向归纳（分析）

基于事实归纳，不凭空新增。官网角色可归并为几个方向时，说明归纳依据。

| 方向 | 来源角色 | 核心痛点 | 官网文案表达的承诺 |
|------|---------|---------|-------------------|

## 3. 场景 ↔ 功能 ↔ 关键词映射（分析）

每个事实场景映射到功能、关键词、承接页。

| 场景 | 角色 | 功能 | 关键词 | 承接页 |
|------|------|------|--------|--------|
```

**写作要点**：
- **事实优先**：官网怎么呈现就怎么记录，保留原始句式与结构细节；不虚构角色或文案
- **分析基于事实**：归纳、映射必须能追溯到上面的事实来源，不引入来源之外的内容
- **不套无关章节**：用户旅程、未覆盖场景等模板章节**除非用户明确要求或信息明确存在，否则不写**；写任何分析都要有事实依据
- **≥3 个 Persona**（基于事实）；场景描述用**口语化表述**（用户真实搜索时的说法）

### 2.7 增长策略文档 `{name}-growth-strategy.md`

**职责**：增长渠道规划与内容策略。回答"从哪里获客、以什么内容触达、按什么节奏执行"。与关键词优先级和竞品差距直接挂钩。

**章节模板**：
```markdown
# {品牌名} — 增长策略

## 1. 增长渠道规划

| 渠道方向 | 目标 Persona | 内容类型 | 优先级 | 预期效果 |
|----------|-------------|---------|--------|---------|

## 2. 内容主题与栏目

| 栏目/主题 | 对标关键词（P0/P1） | 内容形式 | 发布节奏 | 承接页 |
|-----------|-------------------|---------|---------|--------|

## 3. 战役节奏

短期（0–3 个月）/ 中期（3–6 个月）/ 长期（6–12 个月）行动计划。

## 4. 竞品差异化方向

基于 competitors.md 的差距分析，提炼本品可攻克的增长机会。

## 5. 度量指标

建议跟踪的核心 KPI（流量、转化、排名等）。
```

---

*关联：[主文档](./{name}.md) | [keywords](./{name}-keywords.md) | [competitors](./{name}-competitors.md) | [use-cases](./{name}-use-cases.md) | [features](./{name}-features.md) | [site-structure](./{name}-site-structure.md)*

*Last updated: YYYY-MM-DD*
```

**写作要点**：
- 渠道方向必须与 Persona 对齐（使用 use-cases.md 中定义的 Persona 标签）
- 内容主题链接到 keywords.md 的 P0/P1 优先级
- 战役节奏标注时间线，区分短期可落地与中长期布局
- 差异化方向基于真实竞品差距（非凭空设想）
- 度量指标需可追踪，标注建议工具

**最低深度**：
| 维度 | 要求 |
|------|------|
| 渠道方向 | ≥3 个，每个标注对应 Persona |
| 内容主题 | ≥5 个，每个对标 P0/P1 关键词 |
| 战役节奏 | 短期+中期各 ≥3 条计划 |
| 竞品方向 | ≥2 个差异化切入点 |

**常见错误**：
- ❌ 渠道方向不与 Persona 对齐，变成通用营销列表
- ❌ 内容主题不链接关键词优先级，变成随机选题
- ❌ 战役节奏缺少时间线和可执行步骤

## §4 样式指南

### 4.1 标题层级

| 层级 | 用途 | 每文件数量 |
|------|------|-----------|
| `# H1` | 文档主标题 | **1 个** |
| `## H2` | 一级章节 | ≤8 |
| `### H3` | 二级小节 | 不限 |
| `#### H4` | 细分项 | 慎用 |

### 4.2 格式

- 无序列表用 `-`，不超过 3 层
- 有序列表用于步骤、优先级排序
- 关键词首次出现用 **粗体**
- 表格用标准 Markdown 格式，首行有分隔线
- 引用块 `>` 用于：正文内的重要说明、待确认事项、外部引用 — **不用于文档级元信息**（见 §4.6）

### 4.6 文档元信息位置 ⭐

**原则**：标题后是读者最需要的内容；阶段、官网、日期、task 等管理型信息一律放**文档最底部**。

| 位置 | 放什么 | 不放什么 |
|------|--------|----------|
| **标题下（正文区）** | 直接进入首个 `##` 章节 | blockquote 元信息；正文「来源：」「见 xxx.md」「暂不抢」等跨文档引用 |
| **文档底部** | 阶段、Last updated、关联 task | 官网 URL、关联文档列表（改放关联文档节） |
| **信息源节**（正文末） | 全部外部 URL + 用途；同域子路径合并为一行 | 正文「来源：」行、footer 重复官网 |
| **关联文档节**（信息源之后） | 仓库内文档互链、canonical 约束、已有 blog 分工、后续站内动作 | 正文「见 xxx.md」「暂不抢」等 scattered 引用 |

**底部元信息模板**（专题调研、Skill 包、子文档通用）：

```markdown
---

*阶段*：调研 / 执行 / 归档  
*Last updated*：YYYY-MM-DD  
*关联 task*：[TASKS.md](../../TASKS.md) · {client}-{序号}
```

**信息源**（正文末第二节，外部 URL **唯一汇总处**）：

```markdown
## 信息源

| 源 | 用途 | URL |
|----|------|-----|
| {站点名} | {覆盖内容} | https://... |

正文不写「来源：」行；同域子路径并入主站一行。
```

**关联文档**（信息源之后、footer 之前，仓库内引用 **唯一汇总处**）：

```markdown
## 关联文档

| 文档 | 用途 |
|------|------|
| [{name}-glossary.md](./{name}-glossary.md) | canonical 词；暂不抢 xxx |
| [blog/…](./blog/…) | 已有文章分工、互链 |

**后续动作**（非本阶段）：…
```

正文不写「见 xxx.md」「暂不抢」等跨文档说明；footer 仅保留阶段 / Last updated / 关联 task。

**例外**：
- 主文档 `{name}.md` 头部保留 **文档导航表**（§3.1）
- Demo 状态（§11.3）写入底部元信息，或填入客户概览表的「更新日期」字段，**二选一，不重复**
- 七核心子文档底部：`关联` + `Last updated`（已在 §2 模板中）

### 4.3 日期与数字

- 日期：`YYYY-MM-DD`（如 `2026-06-06`）
- 数字：千位分隔符可选，百分比保留一位小数
- 金额：标明币种（`$9.99/月`、`¥99/月`）

### 4.4 术语与大小写

- 品牌名：以官网为准，全文统一
- 首次出现品牌名时标注官网 URL
- 专业术语首次出现时简短解释

### 4.5 敏感信息与数据边界

- **Demo**（`demo/`）：不含真实客户商业数据（预算、报价、合同等）
- **Clients**（`clients/`）：客户预算、报价、合同**不写入**品牌文件夹，单独存放
- 关键词/竞品数据标注抓取日期；活跃客户（`clients/` 非 `others/`）核心数据建议 **≤6 个月**更新一次
- 不确定结论用「初步判断」「待验证」等审慎措辞（标注规范见 §12.2）

## §7 执行模式决策树

加载本规范后，第一步：按 §1.1 确定文件结构选型（单文件/多文件），然后确定当前项目所处的执行模式（A/B/C）。

```
扫描项目目录，回答以下问题：

Q1: 七核心文档（keywords / competitors / features / use-cases / site-structure / growth-strategy）是否全部存在？
  → 否 → 模式 A（补齐缺失）
  → 是 → 继续 Q2

Q2: 每份文档是否达到 §5 对应检查表的全部 P0 项？
  → 否 → 模式 A（扩充到 P0 达标）
  → 是 → 继续 Q3

Q3: 是否存在以下熵增信号？
  - 同一事实出现在 ≥2 份文档且表述不一致
  - 同一长表在 ≥2 份文件中完整重复
  - 文档间引用链接指向已删除/重命名的文件
  - "待验证"标记超过 30 天未处理
  → 是 → 模式 B（整理再进入模式 C）
  → 否 → 模式 C

组合使用：模式 B 结束后衔接模式 C；模式 A 达到 L2 后可转模式 C。
```

## §8 模式 A：从零搭建（冷启动）

### 8.0 Phase 0：站点发现（**先于建文件夹**）

**原则**：在 `demo/{name}/` 创建任何文件之前，先完成站点侦察与信息聚合；信息不足时不建文件夹，只维护调研笔记或 Backlog。

**执行清单**（Agent 可复制）：

```
Phase 0 — 站点发现（预计 1 轮对话）
  ① robots.txt     → 抓取策略、Disallow 路径、Sitemap 声明
  ② sitemap.xml    → 索引与子 sitemap 列表（含 lastmod）
  ③ 子 sitemap     → 逐类抓取 URL 模式，统计量级（>200 行明细 → 放 others）
  ④ 首页 + 导航   → read_url(withAllLinks) 聚合内链
  ⑤ 核心产品页    → /pricing、/features、/about、/faq 等（并行读取 ≤5 URL）
  ⑥ 联网搜索       → 产品定位、定价、竞品、App Store 信息
  ⑦ 产出物         → 站点发现摘要（见下方模板），确认后再建 demo/{name}/
```

**Phase 0 退出条件（建文件夹门槛）**：

| # | 门槛 | 通过标准 |
|---|------|---------|
| 1 | 核心路径 | ≥5 条可验证 URL（含页面类型） |
| 2 | 产品理解 | 能写出一句话定位 + ≥3 个功能模块 |
| 3 | 模式决策 | 单文件 vs 多文件已判定（§1.1） |
| 4 | Sitemap | 已解析或标注「无 sitemap / 404」 |
| 5 | 内链图 | 主导航 + 页脚 + 首页 CTA 已聚合 |

**站点发现摘要模板**（Phase 0 产出，可暂存于对话或 `{name}-research.md`，达标后写入 `{name}-site-structure.md` + `{name}-others.md`）：

```markdown
## 站点发现摘要 — {品牌名}
- 访问日期：YYYY-MM-DD
- 官网：https://...
- Sitemap：有/无；子 sitemap 数量；估算 URL 总量
- robots.txt 要点：Allow/Disallow、AI crawler 策略
- 核心路径表（≥5）
- URL 模式归纳（如 /resources/{subject}/{slug}）
- 内链枢纽页（首页、导航、页脚）
- 技术栈初判
- 待验证项
- 建议模式：单文件 / 多文件
```

**Sitemap 明细归档规则**：
- 完整 URL 列表 **>200 行** → 写入 `{name}-others.md` §1 Sitemap 明细，site-structure 只保留模式与统计
- 多子域 / 多 sitemap 索引 → site-structure 写 IA 树，others 写逐文件 URL 抽样

### 8.1 串行依赖执行顺序

> **核心原则：上一份文档的结论作为下一份文档的上下文输入。** 这与 Phase 0 "先理解再建文件夹"的逻辑一致——每份文档都是对前一结论的深化，而非从零开始。每条文档产出的事实直接约束后续文档，从源头消除跨文档矛盾。

Phase 0 达标后再创建 `demo/{name}/`。文档按以下串行依赖链构建，**每步开始前必须先读取上游文档**：

```
Phase 0（无文件夹）：
  站点发现 → 站点发现摘要 → 判定单/多文件模式
    │
    ▼ 建文件夹，开始串行生成
① site-structure.md  ← 纯事实层：URL、IA、技术栈（Phase 0 数据回填）
    │                    依赖：仅 Phase 0 数据，不依赖任何其他文档
    │                    产出：核心路径表、URL 层级、技术栈、内链枢纽
    ▼
② features.md        ← 功能锚点层：产品能力清单
    │                    依赖：① 的 URL 表（每功能标注对应站内 URL）
    │                    产出：功能列表、用户流程、定价、差异化 ★ 标记
    ▼
③ main doc           ← 综合速览层：品牌概览与文档索引
    │                    依赖：① + ②（概览表有据可依，产品摘要引用已验证功能）
    │                    产出：客户概览表、产品定位、各子文档摘要
    ▼
④ keywords.md        ← 关键词策略层：搜索意图与承接映射
    │                    依赖：① + ② + ③（目标页映射到已知 URL + 功能边界）
    │                    产出：4 类意图 × ≥5 词条、目标页映射、内容缺口
    ▼
⑤ competitors.md     ← 竞品分析层：差异化对比
    │                    依赖：② + ④（竞品对比对标已知功能，竞品关键词补充关键词列表）
    │                    产出：≥3 竞品拆解、≥2 场景对比表、SWOT
    ▼
⑥ use-cases.md       ← 场景映射层：官网场景事实 + 分析
    │                    依赖：② + ③（功能锚点 + ICP 来源）
    │                    产出：官网场景事实表、Persona/方向归纳、场景↔功能↔关键词映射表
    ▼
⑦ growth-strategy.md ← 增长策略层：渠道与内容计划
    │                    依赖：④ + ⑤ + ⑥（渠道方向有数据支撑）
    │                    产出：≥3 渠道方向、内容主题、战役节奏
    ▼
⑧ 互链回填           ← 最后一步：统一补充所有文档间的导航链接
                        生成后：每份文档的互链表引用全部已有文件

（可选）{name}-others.md — Sitemap 明细、原始内链表（可在 ① 之后任意时机创建）
```

**两轮目标对应**：
- ①→④ 完成后 → 达到 **L1 草稿**（有可用概览，≥4 个核心文档）
- ①→⑦ 完成后 → 达到 **L2 可展示**（七核心文档全部存在，所有 P0 项通过）
- L2 达标后进入 L3 精炼（模式 C）

> **为什么主文档从首位移到第③位？** 主文档本质是综合文档，内容来自对各子文档的摘要。等 site-structure 和 features 就绪后再写，概览表不会留空或猜测，"产品信息"可以直接引用已验证的功能列表。如果你需要先有主文档做速览，可以在 ① 之后先写一份草稿版主文档，在 ③ 时用完整上下文重写。

### 8.2 各文档联网搜索策略

> 搜索不仅是"获取信息"，也是**填补串行链上下文缺口**的手段。见 §8.5 缺口检测机制。

| 步骤 | 文档 | 缺口触发条件 | 搜索指令（可复制给 Agent） | 最少产出 |
|------|------|-------------|--------------------------|---------|
| ① | 站点结构 | Phase 0 已覆盖 | **Phase 0**：robots.txt + sitemap 索引 + 子 sitemap + 首页 withAllLinks；再读核心页 | 核心路径表 + URL 模式 + 内链枢纽 |
| ② | 功能 | 功能描述和定价来自产品页，上游无详细数据 | `[品牌名] features pricing review` + 逐个抓取功能页 URL | ≥5 功能 + 核心流程 + 定价 |
| ③ | 主文档 | 产品定位和优化建议可能缺行业洞察 | `[品牌名] about product 2026` | 产品摘要 + 定价 + 目标用户 |
| ④ | 关键词 | 搜索量/难度/竞品关键词全需外部数据 | `[品牌名] [品类] alternatives tool software 2026` + `[品类] best [动词] 2026` | ≥4 意图 × ≥5 词条 |
| ⑤ | 竞品 | 竞品信息几乎从零开始——功能/定价/SEO 全需搜索 | `[品牌名] alternatives vs competitors review` + 逐个抓取竞品官网；按 §2.4 入选标准只保留「主要对标 + 知名」竞品 | ≥3 直接竞品（含功能拆解） |
| ⑥ | 使用场景 | 官网场景事实上游不覆盖 | `[品类] use cases for [persona] benefits` + 官网 use cases 区块抓取 + Reddit/G2 用户评论 | ≥3 场景事实 + Persona 归纳 + 映射表 |
| ⑦ | 增长策略 | 行业基准和内容策略案例需外部研究 | `[品类] content marketing growth strategy 2026` | ≥3 渠道方向 |

**搜索禁令**：
- 搜索结果不足时，标注 `⚠️ 联网信息不足，以下为推演` 并用逻辑推演补全
- **禁止**编造不存在的竞品、不实数据、虚构 URL
- 不确定信息标注 `待验证`（标注规范见 §12.2）
- 搜索配额：每步骤 ≤5 次搜索 + ≤3 次 URL 抓取，优先搜索最有信息密度的查询
- 搜索前明确"本次搜索要填补的具体字段"，搜索后对照检查
- 可量化数据（搜索量、市场份额、价格）找不到就标注「待验证」，**禁止凭推断填入**

### 8.3 模式 A 退出条件

- 七核心文档全部存在
- 每份文档通过 §5 对应检查表的**全部 P0 项**
- 文档间互链表完整（每份文档指向其余文档）
- 输出达标报告 + 建议下一步（模式 C 或进入 L3）

### 8.4 串行上下文传递机制

> 本节阐述 §8.1 串行依赖链的设计原理，是 Agent 在逐份生成文档时必须遵循的上下文注入规则。

#### 设计动机

当前规范定义了"该生成什么"（§2 模板）和"质量标准"（§5 检查表），但没有定义**信息传递链路**。传统模式下各文档各自为战，Agent 在生成 `keywords.md` 时不知道自己上一步写了什么功能，容易产出不匹配的结论。事后靠 §9 模式 B 的矛盾诊断修补——这是"先污染后治理"的代价。

串行上下文传递的核心思路：**让文档间的信息流向与文档间的天然依赖关系同构**，从根源上消除矛盾。

#### 依赖关系图

```
                Phase 0 数据（sitemap、内链、技术栈）
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
  ① site-structure        ② features
     (URL/IA/技术栈)         (功能列表/定价)
          │                     │
          └──────┬──────────────┘
                 ▼
          ③ main doc
          (综合速览)
                 │
          ┌──────┴──────┐
          ▼              ▼
  ④ keywords        ⑤ competitors
     (搜索意图)        (竞品对比)
          │              │
          └──────┬───────┘
                 ▼
          ⑥ use-cases
          (Persona/场景)
                 │
          ┌──────┴──────┐
          ▼              │
  ⑦ growth-strategy ←───┘
     (增长策略)
```

> 每步需读取的前置文档与消费的关键事实，详见 §8.1 执行顺序中的依赖关系和产出描述。

#### 上下文注入的标准动作

Agent 在每步开始时执行以下标准动作：

```
1. 读取上游文档列表（从 §8.1 串行链确定）
2. 从每份上游文档中提取"本步消费的事实摘要"，至少包含：
   - 产品名称、定位（来自主文档/features）
   - URL 列表和页面类型（来自 site-structure）
   - 功能名称和差异化标记（来自 features）
   - 关键词和优先级（来自 keywords）
   - 竞品名称和差异点（来自 competitors）
   - Persona 名称和角色（来自 use-cases）
3. 在生成目标文档时，显式引用上游事实：
   - 表格字段对齐（如 features 的"对应页面 URL"必须取自 site-structure）
   - 术语统一（如 Persona 标签全链路复用）
   - 差异分析根植于真实功能（如 competitors 对比表使用 features 中的功能名）
4. 本次产出的关键事实也应结构化输出，供下游文档消费
```

#### 回填策略

当后续文档生成后，可能需要回填某些上游文档的预留字段：

- `keywords.md` → 可在 `competitors.md` 完成后标注 `待补充：竞品关键词分析后回填`
- `features.md` → 可在 `use-cases.md` 完成后回填 `功能 ↔ 场景映射简表`
- 所有文档 → 在步骤⑧统一做互链回填，补充头部导航表

### 8.5 信息缺口检测与定向补充

> 串行上下文传递解决了"已知信息的流动"，但无法解决"信息本身不够"的问题。Phase 0 拿到的品牌信息是站点层面的快照（URL 结构、技术栈、页面类型），越往串行链下游走，信息密度要求越高，缺口越大。本节定义每个步骤的**缺口检测**和**定向搜索补充**流程——与 Phase 0 "先侦察再建文件夹"一致，只是粒度从项目级下沉到文档级。

#### 核心原则

```
每个步骤 = 读取上游文档 → 评估信息缺口 → [有缺口] → 定向搜索/抓取 → 生成
                                         ↓
                                   [无缺口] → 直接生成
```

**判断标准**：上游文档提供的事实是否足以支撑本步骤的表格/字段填充。如果某关键字段只能靠推演填充，则触发搜索补充。

#### 各步骤信息缺口评估

| 步骤 | 文档 | 上游能提供多少实际数据 | 典型缺口 | 是否需要搜索补充 |
|------|------|----------------------|---------|:---------------:|
| ① | site-structure | Phase 0 直接产出 robots/sitemap/内链 | 一般无缺口 | 否（Phase 0 已完成） |
| ② | features | ① 的 URL 表面向功能页定位 | 功能的具体描述、差异化程度、定价细节 | **是**（需访问功能页+联网搜索） |
| ③ | main doc | ①+② 的技术栈/功能/定价 | 产品定位需要外部验证，优化建议需要行业洞察 | 部分（优化建议可能需要搜索行业基准） |
| ④ | keywords | ① 的 URL（做目标页映射）、② 的功能（对齐意图）、③ 的定位 | 搜索量、难度、竞品关键词、长尾词——**全需搜索** | **是**（关键词策略依赖搜索工具/搜索引擎数据） |
| ⑤ | competitors | ② 的功能名（做对比表行头）、④ 的关键词 | 竞品功能拆解、定价、市场份额、SEO 表现——**几乎从零开始** | **是**（竞品信息依赖联网搜索和竞品网站抓取） |
| ⑥ | use-cases | ② 的功能、③ 的 ICP | 官网实际场景文案/角色、用户评价/反馈 | **部分**（官网场景需抓取；用户反馈需搜索） |
| ⑦ | growth-strategy | ④+⑤+⑥ 的综合数据 | 行业增长基准、内容策略案例——**从零开始** | **是**（增长策略依赖行业研究） |

#### 缺口检测清单（Agent 按步骤执行）

```
每步开始时，Agent 回答以下问题：

1. 本步骤需要产出的所有表格/字段中，哪些字段无上游数据支撑？
2. 这些字段：
   - 可否通过搜索补充？      → 触发定向搜索（见 §8.2 搜索策略表）
   - 是否行业常识/逻辑推演？  → 标注「来源：推演」
   - 是否完全无法获取？      → 标注「⚠️ 待验证」
3. 搜索完成后，逐一检查：搜索是否返回了足够信息？
   - 是 → 填入，标注来源 URL + 日期
   - 否 → 标注「⚠️ 联网信息不足，以下为推演」

约束：
- 禁止凭推断填搜索量/市场份额等可量化数据，找不到就标注「待验证」
- 搜索配额：每步骤 ≤5 次搜索 + ≤3 次 URL 抓取，优先搜索最有信息密度的查询
- 搜索前先明确"本次搜索要填补的具体字段"，搜索后对照检查
```

#### 标准补充流程

```
读取上游文档
    ↓
列出"本步骤产出字段 vs 上游数据覆盖"对比表
    ↓
标记缺口字段 + 判断补充方式
    ↓
执行定向搜索/抓取（≤5 次搜索 + ≤3 次 fetch）
    ↓
将搜索结果逐条填入缺口字段，标注来源
    ↓
仍有缺口 → 标注「⚠️ 待验证」+ 缺口原因
    ↓
生成文档
```

#### 与串行上下文传递的关系

```
上下文传递：已有数据在文档间的流动（横向）
信息补充：   缺失数据通过搜索的新增（纵向）

二者互补：
- 能从上流传下来的 → 直接引用（不搜索）
- 上流传不下来的 → 先搜索，搜索结果也传给下游
- 搜索也拿不到的 → 标注待验证，下游知道这是不确定信息
```

## §9 模式 B：存量整理与去重

### 9.1 三诊

| 诊断 | 检查内容 | 方法 |
|------|---------|------|
| ① 矛盾 | 同事实在不同文件表述是否一致 | 关键词/定价/功能描述跨文件比对 |
| ② 重复 | 同一长表/段落是否出现在 ≥2 文件 | 全文搜索关键词表、竞品表 |
| ③ 断链 | 互链是否有效 | 逐条验证 `[text](./file.md)` |

### 9.2 四治

| 问题 | 处理规则 |
|------|---------|
| **事实矛盾** | 以最新来源为准，旧条目移入归档并记录修正日期 |
| **判断矛盾** | 两版并置，各自标注来源和日期，加 `⚠️ 判断差异` 标记 |
| **重复内容** | 按 §3.3 防重复规则处理：保留最对口文件，其余改为 `> 详见 [文件](./file.md)` |
| **断链** | 更新为目标文件当前路径；已删除的文件移除引用行 |

### 9.3 模式 B 退出条件

- 所有事实矛盾已解决（判断矛盾已标记）
- 零重复长表
- 零断链
- 术语跨文档统一
- 输出完整的诊-治报告 + 建议转模式 C

## §10 模式 C：增量精炼

```
入口：七核心文档之一（轮换，见轮换策略）
  ↓
① 对齐：统一术语、修正过时、标记"待验证"
  禁止为缩短篇幅删掉仍有用的段落
  ↓
② 联动：按 §3 依赖矩阵检查关联文档
  ↓
③ 调研：执行 backlog 条目（推演/联网/URL）
  ↓
④ 回填：追加写入对口文档，标注来源和日期
  ↓
⑤ 记增量：更新 Last updated、CHANGELOG
  ↓
下一轮或结束
```

### 10.1 入口轮换策略

| 优先级 | 选择规则 |
|--------|---------|
| P1 | 上一轮产生最多"待验证"标记的文档 |
| P2 | 上一轮改动最大文档的关联文档（按依赖矩阵） |
| P3 | 距上次更新时间最久的文档 |
| 周期 | 七文档至少各做一次入口后，做一次全量审视 |

### 10.2 增量写入规则

| 信息来源 | 处理方式 |
|---------|---------|
| 逻辑推演 | 写入对口文件，标 `来源:推演` |
| 联网/URL | 摘录 + URL + 日期，宁可多一行出处 |
| 用户文件（PDF/纪要） | 结论与要点写入对口文档，保留来源 + 日期 |
| 新功能/定价更新 | 追加段落或表格行，不删旧内容；过时内容标"已弃用" |

**禁止**：以"精炼"为名删除本轮新增要点。若必须缩短，原文移入 others 归档并加链接。

## §11 Demo 三级状态管理 ⭐

这是本规范的核心创新。每个 Demo 项目应处于以下三个级别之一：

### 11.1 级别定义

```
L1 草稿（内部可用）
  用途：内部了解项目基本信息，不适合给客户看
  典型场景：刚刚接触、初步调研、信息收集阶段

L2 可展示（可给客户看） ← Demo 项目的默认目标
  用途：向潜在客户展示分析能力、获取信任
  典型场景：初次沟通、方案演示、pitch 阶段

L3 可毕业（可移交 clients/）
  用途：达到正式交付标准，准备转入 clients 目录
  典型场景：客户签约/付费，需要长期维护
```

### 11.2 各级检查清单

#### L1 草稿 检查清单

| # | 项 | 通过标准 |
|---|----|---------|
| 1 | 主文档存在 | 创建 `{name}.md` |
| 2 | 客户概览表 | 核心字段填满（行业、网站、阶段、产品、日期） |
| 3 | 产品信息 | ≥100 字清晰描述 |
| 4 | 最低文件数 | ≥3 个核心文档有可用内容 |

#### L2 可展示 检查清单

| # | 项 | 通过标准 |
|---|----|---------|
| 1 | 七核心文档 | 全部存在 |
| 2 | P0 检查项 | 全部通过（参见 §5 各表） |
| 3 | 数据来源 | 关键数字标注来源+日期 |
| 4 | 文档互链 | 主文档头部导航表齐全；子文档底部关联链接有效 |
| 5 | 无事实矛盾 | 跨文件检查无冲突 |
| 6 | 格式整洁 | 符合 §4 样式指南 |
| 7 | 可读性 | 非 SEO 专业人员可读懂 |

#### L3 可毕业 检查清单

| # | 项 | 通过标准 |
|---|----|---------|
| 1 | L2 全部满足 | 是 |
| 2 | 模式 C 精炼 | ≥1 轮完整执行 |
| 3 | 数据时效 | 所有数据标注日期，无 >3 个月未更新的 |
| 4 | 健康检查 | 全部指标在健康值内（见 §6 文档健康指标） |
| 5 | 客户确认 | 有明确客户签约/付费 |
| 6 | 迁移前清理 | 移除内部注释、草稿标记 |

### 11.3 状态标注

每个 Demo 项目的主文档**底部**应标注当前状态（或写入客户概览表，二选一）：

```markdown
---

*Demo 状态*：L2 可展示  
*最后评估*：2026-06-06  
*未通过项*：无  
*Last updated*：YYYY-MM-DD
```

### 11.4 从 demo 到 clients 的迁移流程

```
1. 确认 L3 全部通过
2. 复制整个文件夹到 clients/{name}/
3. 移除 Demo 状态标注（§11.3）；主文档更新为正式客户阶段
4. 在 clients/others/ 中移除该项目的旧存档（如有）
5. 在 demo/ 中保留副本或 README 索引指向 clients/ 位置
6. 按 §15 开启 clients 维护约定
```

# 第四篇：Clients 迁移后维护（POST-MIGRATION）

> 本节适用于 `clients/{name}/` 正式客户。高定制化是常态：七核心文件是骨架，之上可自由扩展。

## §15 目录与定制规则

### 15.1 文件夹位置

| 状态 | 路径 |
|------|------|
| Demo 调研 | `demo/{name}/` |
| 活跃客户 | `clients/{name}/` |
| 已停止运营 / 归档 | `clients/others/{name}/` |

### 15.2 定制扩展

在七核心文件之上，按任务自由新增，常见模式：

| 类型 | 命名示例 | 说明 |
|------|----------|------|
| 专项分析 | `{name}-positioning.md`、`{name}-glossary.md` | 单主题深研 |
| 子产品线 | `{name}-{product}.md` | 同一客户多产品 |
| 杂项归档 | `{name}-others.md` | sitemap 明细、合规、数据来源等 |
| 博文 | `blog/{NN}-{slug}-{year}.md` | 对外 SEO 内容 |
| 子文件夹 | `blog/`、专项目录 | 材料较多时拆分 |

**原则**：按 §3.3 防重复规则，同一长表只保留一处；不强制所有客户文件结构一致。

### 15.3 补充材料后缀

同一客户的新增材料可用后缀区分，避免覆盖已有文档：

| 后缀 | 含义 |
|------|------|
| `-draft` | 补充草稿 |
| `-copy` | 从混合来源提取的片段 |
| `-supplement` | 补充分析 |

### 15.4 归档流程

客户停止运营时：整文件夹移至 `clients/others/{name}/`，概览表标注「已停止运营」。

### 15.5 新客户 onboarding

从 **demo 毕业** 或从 **结构最接近的现有 clients 案例** 复制起点，逐文件填充；不建议从完全空白开始。

### 15.6 质量底线（clients）

| 检查项 | 通过标准 |
|--------|---------|
| 七核心文件 | 活跃客户至少保留（可大量扩展，不可全部删除） |
| 命名一致 | `{name}-{topic}.md`，`{name}` 全小写连字符 |
| 数据时效 | 关键词/竞品等标注来源与日期；活跃客户 ≤6 个月 |
| 无重复 | 按 §3.3 防重复规则，同一主题不出现在两个文件中 |
| 敏感信息 | 预算/报价/合同不在品牌文件夹 |

## §12 通用 Agent 指令框架

### 12.1 输出格式

每步执行结束，Agent 输出：

```markdown

## 本次上下文注入

> **串行链追踪**：Agent 应始终知晓当前在串行链上的位置（步骤 X/7）和下一步的目标文档。

### 12.2 通用规则

| 规则 | 说明 |
|------|------|
| 信息溯源 | 联网摘录必须附带 URL + 访问日期 |
| 待验证标注 | 不确定信息标注 `⚠️ 待验证`；标注格式：`⚠️ 待验证` + 缺口原因（如"需 Semrush 验证""需用户访谈确认"）；可量化数据（搜索量/份额/价格）找不到就标注，禁止凭推断填入；定期清理超过 30 天未处理的待验证标记（见 §6 健康指标） |
| 禁止编造 | 不存在的事实标注"无法确认"，不编造 |
| 禁止抄袭 | 联网摘录宜短并改写，不大段复制 |
| 追加优先 | 模式 C 禁止以精炼为名删除内容 |

### 12.3 术语规范

| 术语 | 标准用法 |
|------|---------|
| 产品名称 | 以官网为准，全文统一 |
| 竞品名称 | 以竞品官网为准 |
| Persona 标签 | 主文档定义后在子文档统一使用 |

## §13 文档级 Agent 指令

以下是针对每类文档的专用生成指令，可直接复制给 Agent 使用。**重要：每条指令开头标注了需遵循的上下文传递规则（§8.4）和缺口检测机制（§8.5）。**

> 步骤编号对应 §8.1 串行依赖链。文档顺序为 ①→②→③→④→⑤→⑥→⑦→⑧。

### 13.1 站点结构（步骤 ① / 7）

```markdown
你是技术 SEO 分析师。在创建 demo/{name}/ 文件夹之前，先完成 Phase 0 站点发现。

Phase 0 任务：
1. 读取 robots.txt、sitemap.xml 及全部子 sitemap
2. 用 read_url(withAllLinks) 抓取首页与主导航页，聚合内链
3. 并行读取 ≤5 个核心产品页（/about、/faq、/pricing 等）
4. 联网搜索：定价、App Store、竞品线索
5. 输出「站点发现摘要」，确认达标后再建文件夹

建文件夹后写入 {name}-site-structure.md：
1. 核心路径表 ≥5 条（含页面类型、目标关键词、优先级）
2. URL 层级 / IA 树
3. Sitemap 与 URL 模式表（量级统计；明细 >200 行 → others.md）
4. 内链枢纽表
5. 技术栈（标注识别方式）
6. URL 分阶段规划（链接 keywords 优先级）

格式要求：
- 每条 URL 标注访问日期；不确定标「待验证」
- 禁止编造不存在的路径

上下文注入：
- 本步骤为串行链起点，仅依赖 Phase 0 站点发现摘要
- 无需读取其他文档
```

### 13.2 功能文档（步骤 ② / 7）

```markdown
你是产品分析师。你需要为 {品牌名} 创建功能文档（{name}-features.md）。

> 遵循 §8.4 上下文传递规则，执行前读取上游文档 | 上游：{name}-site-structure.md

任务：
1. 列出 ≥5 个核心功能，每个标注差异化程度
2. 描述用户核心操作流程
3. 记录定价结构和套餐差异
4. 功能 ↔ 关键词映射简表（先留空，待 keywords 完成后回填）

格式要求：
- 功能描述用用户语言
- 差异化用 ★ 标记
- 每个功能标注对应的站内 URL（取自 site-structure.md 的核心路径表）
- 如果 site-structure 中缺少某功能的页面，标注「URL 待确认」

上下游：
- 上游依赖：site-structure.md（URL 映射锚点）
- 产出将用于：main doc（产品摘要）、keywords（功能边界）、competitors（差异化对比）、use-cases（功能↔场景映射）
```

### 13.3 主文档（步骤 ③ / 7）

```markdown
你是 {品牌名} 的产品分析师。你需要创建主文档（{name}.md）。

> 遵循 §8.4 上下文传递规则，执行前读取上游文档 | 上游：{name}-site-structure.md, {name}-features.md

任务：
1. **先填定位表**（品类、价值主张、竞争替代、差异化锚点、市场位置）
2. 撰写定位简述 2–3 段（品类格局+本品位置、核心用户画像、品牌存在理由）
3. 填写客户概览表（行业、网站、阶段、产品、日期、形态、差异化、目标用户、市场）
4. 撰写产品信息（受众、产品线、定价摘要——直接引用 features.md）
5. 为每份子文档撰写 3-5 行摘要（已存在的：site-structure、features；未创建的标注"（待生成）"）
6. 提供 1-3 条具体的 SEO/GEO 优化建议（需搜索行业基准验证可行性）

格式要求：
- 使用 §2.1 模板结构
- 定位表 5 个维度必须填满，差异化锚点需与 features ★ 标记一致
- 价值主张禁止凭空编造——优先使用搜索到的用户真实表述
- 定位简述 2–3 段，不展开成独立文章
- 客户概览表不留空
- 优化建议需具体（如"创建 vs 对比页"而非"优化 SEO"）
- 底部标注关联与 Last updated 和创建日期

上下游：
- 上游依赖：site-structure.md + features.md
- 产出将用于：keywords（产品定位和受众）、use-cases（ICP 定义）、competitors（差异化锚点作为对比基准）
```

### 13.4 关键词文档（步骤 ④ / 7）

```markdown
你是 SEO 分析师。你需要为 {品牌名} 创建关键词文档（{name}-keywords.md）。

> 遵循 §8.4 上下文传递规则，执行前读取上游文档 | 上游：{name}-site-structure.md, {name}-features.md, {name}.md

任务：
1. 按 4 类意图（导航/信息/商业/交易）组织关键词，每类 ≥5 条
2. 每条标注目标页和优先级（P0/P1/P2）——目标页必须取自 site-structure.md 中的真实 URL
3. 识别内容缺口（高搜索量但站内无覆盖的词）

格式要求：
- 使用 §2.2 模板
- 数据标注来源工具+日期（如 "Semrush 2026-05" 或 "Google 搜索结果 2026-05"）
- P0 为必须覆盖的词
- 目标页映射率 ≥80%（URL 不存在则标注「待建页」）
- 搜索量/难度缺失时标注「⚠️ 待验证：建议用 Semrush/Ahrefs 查询」

上下游：
- 上游依赖：site-structure.md + features.md + main doc
- 产出将用于：competitors（竞品关键词发现）、growth-strategy（内容计划关联关键词优先级）
```

### 13.5 竞品文档（步骤 ⑤ / 7）

```markdown
你是竞品分析师。你需要为 {品牌名} 创建竞品文档（{name}-competitors.md）。

> 遵循 §8.4 上下文传递规则，执行前读取上游文档 | 上游：{name}-features.md, {name}-keywords.md

任务：
1. 先按 §2.4 竞品入选标准筛选竞品——只保留**主要对标竞品**（与本品争夺同一批用户/场景）且**知名**（公开融资可查、或月访问量十万级、或行业公认头部）的产品；剔除泛品类参照物（如 LLM 网关、模型 API）与流量/融资均无公开数据的小众初创
2. 锁定 ≥3 个直接竞品进行详细拆解
3. 创建 ≥2 张场景级对比表（表头使用 features.md 中的功能名）
4. 分析本品 vs 竞品的差异化机会（基于 features.md 中 ★ 标记的差异化功能）

格式要求：
- 每个竞品标注定位、用户、功能、价格、差异
- 流量/排名数据标注来源 + 日期（找不到就标注「待验证」）
- 不确定信息标"待验证"
- 竞品关键词发现 → 标注，待下一步回填到 keywords.md

上下游：
- 上游依赖：features.md + keywords.md
- 产出将用于：growth-strategy（竞品差距 → 增长机会）、keywords.md 回填（竞品关键词）
```

### 13.6 使用场景文档（步骤 ⑥ / 7）

```markdown
你是用户体验分析师。你需要为 {品牌名} 创建使用场景文档（{name}-use-cases.md）。

> 遵循 §8.4 上下文传递规则，执行前读取上游文档 | 上游：{name}-features.md, {name}.md

任务：
1. 记录官网/产品实际呈现的使用场景事实（角色、文案、结构细节），保留原句式，标注来源
2. 基于事实归纳 Persona / 方向（≥3 个，标注归纳依据）
3. 创建场景 ↔ 功能 ↔ 关键词映射表（功能名取自 features.md，关键词取自 keywords.md）

格式要求：
- 事实优先：官网怎么呈现就怎么记录，不虚构角色或文案
- 分析必须能追溯到事实来源，不写来源之外的内容
- 不套无关章节（用户旅程、未覆盖场景等），除非用户明确要求或信息明确存在
- 场景描述用口语化表述（优先使用从用户评论/论坛中提取的真实表述）
- 映射表链接到 features.md 和 keywords.md
- Persona 标签在全文统一，下游文档复用

上下游：
- 上游依赖：features.md + main doc
- 产出将用于：growth-strategy（Persona → 目标人群 → 内容类型）
```

### 13.7 增长策略（步骤 ⑦ / 7）

```markdown
你是增长分析师。你需要为 {品牌名} 创建增长策略文档（{name}-growth-strategy.md）。

> 遵循 §8.4 上下文传递规则，执行前读取上游文档 | 上游：{name}-keywords.md, {name}-competitors.md, {name}-use-cases.md

任务：
1. 列出 ≥3 个渠道方向（每个标注对应的 Persona）
2. 建议内容主题和栏目（与 keywords 优先级对齐）
3. 提供短期/中期战役节奏

格式要求：
- 每个渠道标注目标人群和内容类型
- 内容主题链接到 keywords.md 的优先级
- 战役节奏标注时间线
- 渠道方向与 Persona 对齐（使用 use-cases.md 中定义的 Persona 标签）

上下游：
- 上游依赖：keywords.md + competitors.md + use-cases.md
- 终点文档：串行链最后一份分析文档，完成即达到 L2
```
